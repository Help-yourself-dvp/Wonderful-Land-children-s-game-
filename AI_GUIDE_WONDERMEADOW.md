# AI Guide — проект «Волшебная полянка»

Адаптация универсального AI_GUIDE.md владельца под проект детской развивающей игры
(Three.js + Vite + Capacitor, Android APK через GitHub Actions).
Из исходного гайда убрана специфика проекта FitFlow (здоровье, уведомления, датчики,
голосовой помощник, виджеты) — для детской офлайн-игры это неприменимо.
Сознательное отличие: приоритет «полного набора разрешений» заменён на
**«ноль разрешений»** (см. ГДД раздел 6.4).

---

## Основной принцип
Максимально быстро получить стабильный рабочий результат.
Работающая игра важнее идеального кода. Каждое изменение делает проект лучше,
но не увеличивает сложность без необходимости.

## Принцип обратной связи
Комментарии владельца — предложения к обсуждению, а не безусловные задачи.
AI обязан:
- отвечать по каждому пункту владельца, без пропусков и объединений;
- при несогласии — честно сказать и аргументированно предложить альтернативу;
- финальное слово всегда за владельцем.

## Как не раздувать диалог и не ждать долгих ответов

Главное правило: **один законченный спринт — один диалог**. После коммита, CI и
отчёта лучше открыть новый диалог. Код и документы уже лежат в репозитории, поэтому
вся старая переписка новому агенту не нужна.

1. В конце спринта записать в документах: версию, SHA, что проверено и следующий шаг.
2. В новом диалоге попросить сначала прочитать `AI_GUIDE_WONDERMEADOW.md`,
   `ОПИСАНИЕ_ИГРЫ.md`, `ГДД.md`, `README.md` и `ЧЕКЛИСТ_ТЕСТОВ.md`.
3. Не переносить в новый диалог старые скриншоты, APK, логи и большие куски кода.
4. `src/main.js` не читать целиком: искать нужное место и открывать небольшой отрывок.
5. Скриншоты делать только для важной визуальной проверки или поиска ошибки.
6. Сначала запускать короткие проверки: build, ошибки консоли и состояние DOM.
   Только затем — нужные кадры Playwright.
7. В чат отправлять короткий нумерованный итог и ссылки, а не полные логи и diff.
8. Если диалог уже стал медленным, не пытаться «лечить» его новыми вложениями:
   сохранить текущий результат в Git и документах, затем продолжить в новом диалоге.

Так история проекта не теряется, но каждый новый разговор остаётся лёгким.

## Уровень владельца
Не профессиональный разработчик. Инструкции — для начинающего: пронумерованные
шаги, что открыть, куда нажать, что вставить. Владелец читает ответы с телефона:
ссылки — прямые и кликабельные, полные URL. Ссылки на правку файлов GitHub давать
в режиме редактирования (`.../edit/<ветка>/<путь>`).

## Стиль ответов
Меньше обсуждений — больше готовых решений: краткое объяснение, пошаговые действия,
полностью готовый код. Мелкие технические решения AI принимает сам. Согласование —
только если меняются: функциональность, архитектура, безопасность данных детей,
совместимость версий.

## Работа с кодом и версиями
- Малое изменение — не присылать целый файл, только заменяемый блок/функцию.
- Одна версия = одна небольшая законченная задача. Не смешивать изменения в релизе.
- Каждая новая версия устанавливается поверх предыдущей, сохранения ребёнка не теряются.
- Стабильность важнее новых функций. Не переписывать рабочий код без причины.

## Зависимости
Новые библиотеки/Capacitor-плагины — только при реальной необходимости и после
оценки рисков. Чем меньше зависимостей — тем легче сборка в Actions.

## Приоритет разработки
1. Исправление ошибок → 2. Стабильность → 3. Удобство ребёнка и родителя →
4. Упрощение процесса → 5. Новый функционал → 6. Косметика.

## Документация проекта
Главный документ: **ГДД.md**. Каждый законченный спринт сверяет и при необходимости
обновляет `ОПИСАНИЕ_ИГРЫ.md`, `ГДД.md`, `AI_GUIDE_WONDERMEADOW.md`, `README.md` и
`ЧЕКЛИСТ_ТЕСТОВ.md`; выпуск — ещё и `RELEASE_NOTES.md`. Не нужно переписывать разделы
ради объёма, но версия, фактическое поведение, проверки и следующий шаг должны совпадать.
`THIRD_PARTY.md` хранит лицензии ассетов. `PRIVACY.md` понадобится для RuStore с простой
формулировкой: «приложение офлайн, ничего не собирает и не передаёт».

## Доступ к GitHub — простое объяснение

### Три варианта

1. **Обычный доступ Arena — использовать первым.**
   Чаще всего владельцу ничего делать не нужно: агент сам читает код, делает commit,
   push и Pull Request через уже подключённый GitHub.

2. **Device Flow — расширенный доступ через короткий код.**
   Он нужен, если обычный доступ не позволяет изменить `.github/workflows`, запустить
   Actions или выпустить Release. Агент показывает ссылку
   https://github.com/login/device и короткий код. Владелец вводит код на GitHub и
   нажимает подтверждение. Пароль, 2FA-код и секрет в чат не отправляются.

3. **Токен с ограниченным сроком — только запасной вариант.**
   Его можно вручную создать на несколько дней, разрешить только нужный репозиторий и
   только нужные действия. Это сложнее Device Flow. Токен нельзя присылать в чат,
   вставлять в ссылку, commit или лог. Хранить его можно только в защищённом секрете
   среды или во временном файле вне репозитория; после работы файл удалить, доступ
   отозвать или дождаться короткого срока окончания.

### Важно: код Device Flow — не отдельный вид ключа

Короткий код нужен только для подтверждения на сайте. После подтверждения GitHub
выдаёт агенту **OAuth-токен**. Поэтому «войти по коду» и «получить OAuth-токен» —
два шага одного способа, а не два разных вида доступа. Сам короткий код быстро
истекает и не заменяет токен.

### Можно ли обойтись без кода и токена

- **Да**, если обычный доступ Arena выполняет всю задачу. Ничего дополнительно
  подключать не нужно.
- **Нет**, если GitHub отклоняет именно действие, для которого у Arena нет права —
  например, правку workflow, ручной запуск Actions или публикацию Release. Тогда
  владелец должен либо расширить права GitHub App, либо один раз подтвердить Device
  Flow. Агент не может честно «обойти» запрет GitHub.
- Ручной ограниченный токен не обязателен: обычно Device Flow проще.

### Как отозвать OAuth-доступ

1. Открыть https://github.com/settings/applications
2. Выбрать **Authorized OAuth Apps**.
3. Открыть **GitHub CLI**.
4. Нажать **Revoke access** и подтвердить.

Это удаляет только ключ доступа. Репозиторий, код, коммиты, Actions и Releases
останутся на месте. Удаление локального файла с токеном не заменяет отзыв на GitHub.

### Короткая памятка агенту

- Сначала использовать обычные `git` и `gh`.
- Если не хватает права `workflow`/Actions — применить Device Flow со scopes
  `repo workflow`; не просить пароль, PAT, токен или 2FA-код в чате.
- Секрет не печатать. Временный `/home/user/gh_access.json` держать вне репозитория и
  удалить после работы.
- В этой среде OAuth проверен через `API.GITHUB.COM` в верхнем регистре и заголовок
  `Authorization: Bearer …`. Для workflow при необходимости использовать Git Data API.
- CI искать только по полному SHA. Если CDN снова отвечает `EOF`, не повторять
  одинаковые скачивания: сверить успешный run, SHA-256 APK, сертификат и Release API.
- После push завершить CI, проверку подписи и Release, а затем отозвать временный OAuth.

## Подпись APK (keystore) — РЕШЕНО окончательно (v0.9.1, b20)

**Корневая причина всех мучений:** Android Gradle Plugin молча генерировал НОВЫЙ случайный
debug-ключ на каждой сборке CI (в сертификате notBefore = время билда), хотя keystore из
секрета клался и в android/app/, и в $HOME/.android/. Простого наличия файла недостаточно —
AGP его игнорировал.

**Рабочее решение (не ломать!):** в workflow шагом «Pin debug signing» ключ жёстко
прописывается в `android/app/build.gradle`:

```gradle
signingConfigs { debug { storeFile file('debug.keystore'); storePassword 'android';
keyAlias 'androiddebugkey'; keyPassword 'android' } }
```

- Ключ `debug.keystore` (PKCS12, alias `androiddebugkey`, пароль `android`, до 2056 г.)
  сгенерирован один раз 14.08.2026 и лежит в секрете **`DEBUG_KEYSTORE_BASE64`**
  (libsodium sealed box, скрипт /home/user/set_secret.py).
- Контроль стабильности в логе CI: sha256 файла keystore (должен быть
  `a918cd167f3cdc646a4fee5f979bb5c3e44253a7830d4d27630db81b2d422199`) и **стабильный
  отпечаток сертификата `50:7E:7D:84:69:A2:8B:7B:8A:91:B7:85:B9:BA:6B:AA:93:4D:91:97:87:79:A7:FF:02:F8:F7:ED:A3:DA:85:5B`**
  (также в /home/user/expected_cert.txt). Получить из APK:
  `unzip -p app.apk META-INF/CERT.RSA | openssl pkcs7 -inform DER -in /dev/stdin -print_certs | openssl x509 -noout -fingerprint -sha256`
- ⚠️ Хэш сырого `META-INF/CERT.RSA` для контроля НЕ годится: PKCS#7 содержит метку
  времени подписи, поэтому он меняется при КАЖДОЙ подписи даже одним ключом.
  Сравнивать можно только fingerprint самого сертификата.
- Подтверждено: b19 (случайный) → b20 (наш ключ, совпадение 1:1).
- Резервная копия ключа: `debug.keystore` в корне воркспейса песочницы — владельцу
  скачать один раз и хранить. Потеря и секрета, и копии = конец обновлениям «поверх».
- Перед публикацией в RuStore решить: оставить debug-подпись (допустимо для
  некоммерческого приложения) или сгенерировать релизный ключ тем же способом.

## Релизный процесс (эталон, обновлён в v0.18.0)
1. Версия живёт в `version.txt`; workflow читает её автоматически (`run: echo "APP_VERSION=..."`).
   Текст текущего выпуска хранится в `RELEASE_NOTES.md` и обновляется вместе с версией.
2. Push в `main` автоматически собирает APK и сохраняет артефакт `wonder-meadow-apk`.
   В рабочей ветке агент запускает тот же `build.yml` через `workflow_dispatch`.
3. Основной автономный путь публикации: ручной запуск с `publish_release=true` и
   `release_target=<полный проверенный SHA или main>`. Runner создаёт/обновляет публичный
   Release `v<version>` и загружает стабильное имя `wonder-meadow-<version>.apk`.
4. Резервный старый путь: AI скачивает Actions artifact и создаёт Release через API.
   Его не повторять много раз при `EOF` blob-хранилища — использовать пункт 3.
5. Перед сообщением «готово» обязательно сверить: `conclusion=success`, полный `head_sha`,
   `version.txt` = тегу, Release публичный и asset имеет ненулевые размер/digest. Workflow
   сам сравнивает SHA-256 сертификата с эталоном
   `50:7E:7D:84:69:A2:8B:7B:8A:91:B7:85:B9:BA:6B:AA:93:4D:91:97:87:79:A7:FF:02:F8:F7:ED:A3:DA:85:5B`
   и публикует результат в теле Release. Если CDN доступен песочнице — дополнительно
   скачать APK и проверить локально; сетевой `EOF` после успешных проверок выше честно
   отметить как ограничение среды, а не как ошибку APK.

## Метод «Совет участников» (принят 14.08.2026, зафиксирован навсегда)
Любое решение, ВИДИМОЕ пользователю (тексты, названия, подписи, тональность,
экраны для родителей), AI прогоняет через четырёх персон и приводит вердикт каждой:
1. **Психолог (возраст 3–6)** — не инфантилизирует ли? не пугает ли? уважает ли
   гордость ребёнка за «я уже большой»? нет ли давления и оценочных суждений?
2. **Родитель** — снимает ли вину «опять планшет»? видна ли польза и безопасность?
3. **Маркетолог** — коротко? читается за секунду? пригодно для RuStore-описания?
4. **Критик** — есть ли штампы («развивающая», капс, восклицания)? не из 2000-х ли вид?
Финальная формулировка — компромисс четырёх вердиктов; спорные случаи — владельцу
как развилку. Пример-эталон: подпись заставки «Добрые приключения с пользой»
(вместо «сказочный мир для малышей»: «малыш» отвергнут психологом как инфантилизм
для 5–6 лет).

## Специфика детского проекта (добавлено при адаптации)
1. **Ноль разрешений Android** в манифесте. Новое разрешение — только по решению владельца.
2. **Ноль сетевых запросов из игры** — офлайн по определению. Внешние ссылки — только
   из родительского уголка за Parent Gate.
3. Никакой аналитики/рекламных SDK — ни при каких сценариях.
4. Озвучка NPC — заранее сгенерированные локальные аудиофайлы; никаких онлайн-TTS.
5. Превью для владельца: встроенная панель превью песочницы + **одиночный HTML-файл**
   (весь код встроен, работает в просмотрщике файлов без сети). Жёсткая проверка —
   всегда на реальном APK на устройстве владельца.
6. Данные о прогрессе и статистике ребёнка — только на устройстве; обновления APK
   не должны их терять (миграции сохранений предусматривать заранее).

## Накопленный опыт (перенесённый)
- Любое изменение проверять небольшими итерациями; рабочий код предпочтительнее «идеального».
- Перед изменением инфраструктуры сначала проверить, решается ли задача без него.
- Если изменение касается только интерфейса — не трогать логику.
- После правок HTML/JS проверять: все функции из addEventListener существуют, все ID
  на месте; querySelectorAll возвращает NodeList без .some/.map/.filter — приводить
  через Array.from().

## Три бесплатные пробы скина — совсем простая инструкция владельцу

**Главное:** всё делается прямо в текущем диалоге Arena. Владельцу не нужно ставить
ComfyUI/Blender, искать видеокарту, регистрировать платный аккаунт, вводить карту или
передавать пароль/токен. Если сайт просит оплату — ничего не оплачивать и закрыть его.
Локальную техническую часть выполняет агент. Результаты в игру автоматически не попадают:
сначала владелец выбирает или отклоняет вариант.

### Перед началом — одно сообщение от владельца

1. В текущем диалоге нажать на поле сообщения внизу.
2. Написать по шаблону: **«Герой: Ёжик. Хочу: добрые крупные глаза, меньше колючек,
   тёплый зелёный шарфик»**. Можно выбрать Сову или Светлячка и любые 2–3 простых пожелания.
3. Если есть **собственный** рисунок, нажать скрепку рядом с полем сообщения и приложить
   PNG/JPG. Это необязательно. Не прикладывать фотографии детей, чужих мультгероев и
   изображения с неясными правами.
4. Нажать кнопку отправки. Этого достаточно для старта всех трёх проб.

### Проба 1 — бесплатный контрольный скин прямо в игре

**Что делает агент:** создаёт 3 лёгких процедурных варианта в Three.js без внешней модели,
собирает один автономный HTML и одну картинку-сравнение. Это контрольная точка: ИИ-вариант
дальше должен быть заметно лучше неё.

**Что нажимает владелец:**

1. В сообщении агента нажать на файл превью — он откроется в просмотрщике Arena.
2. На телефоне повернуть экран горизонтально.
3. Посмотреть варианты 1, 2 и 3 в общем мире и крупно.
4. Вернуться в диалог и написать, например: **«Проба 1: вариант 2. Глаза нравятся,
   шарфик сделать светлее»**. Если ни один не подходит, так и написать.

**Что сохранить:** номер выбранного варианта и одну короткую причину. Картинку сохранять
необязательно; агент оставляет исходники и превью в проекте. Цена и внешние аккаунты — 0.

### Проба 2 — бесплатный локальный 2D ИИ-концепт

**Что делает агент:** локально запускает бесплатный
[ComfyUI](https://github.com/comfyanonymous/ComfyUI) с
[FLUX.1-schnell](https://huggingface.co/black-forest-labs/FLUX.1-schnell). На 17.08.2026
веса FLUX.1-schnell опубликованы под Apache-2.0 и разрешают коммерческое использование;
перед фактической загрузкой агент ещё раз открывает карточку именно этой ревизии и
фиксирует лицензию. Детские фотографии никуда не загружаются. Готовится лист из 4 образов,
а не бесконечная генерация.

**Что нажимает владелец:**

1. После Пробы 1 написать в этом же диалоге: **«Запускаем Пробу 2 для варианта 2»**.
2. Когда агент приложит лист, нажать на картинку, чтобы открыть её крупно.
3. По очереди посмотреть A, B, C и D. Лучше оценивать не «красивую картинку вообще», а
   три вещи: добрый ли взгляд, узнаётся ли герой, читается ли силуэт на маленьком экране.
4. Вернуться в диалог и написать: **«Проба 2: B»** и при желании одну правку.

**Что сохранить:** выбранный прозрачный PNG и текстовый файл с источником/лицензией.
Скачивать вручную не нужно: агент сохраняет только одобренный кандидат. Если локальная
машина без подходящей видеокарты, пробу не переносят в платный API: её откладывают или
выполняют на доступной бесплатной локальной машине.

### Проба 3 — бесплатный черновик 3D

**Что делает агент:** только выбранный собственный 2D-концепт пробуется локально в
[InstantMesh](https://github.com/TencentARC/InstantMesh) (Apache-2.0) и, для честного
сравнения, в [TripoSR](https://github.com/VAST-AI-Research/TripoSR) (карточка модели на
17.08.2026 указывает MIT). Затем бесплатный [Blender](https://www.blender.org/) используется
для очистки, уменьшения полигонов и экспорта GLB. Облачные «бесплатные кредиты» не нужны.

**Что нажимает владелец:**

1. В этом же диалоге написать: **«Запускаем Пробу 3 для концепта B»**.
2. В ответе агента нажать на автономный HTML с вращающейся моделью.
3. Повернуть телефон горизонтально и провести пальцем по модели, чтобы посмотреть спереди,
   сбоку и сзади. Затем открыть картинку «в мире игры» на 812×375.
4. Ответить тремя короткими строками: **«Узнаётся: да/нет. Силуэт приятный: да/нет.
   В игре видно хорошо: да/нет»**.

**Что сохранить:** только если все три ответа «да» — черновой `.glb`, выбранный PNG,
скриншот 812×375 и `LICENSE_SOURCES.md` с точными ссылками и лицензиями. Риг и анимация
проверяются отдельно; сырой image-to-3D результат не заменяет героя автоматически.

### Когда проба считается законченной

- Есть один выбранный номер/буква либо честное решение «старый вариант лучше».
- Есть сравнение в игровом кадре 812×375, а не только красивый портрет.
- Источники и лицензии записаны; сеть в самой Android-игре не появилась.
- Владелец ничего не оплатил и не передавал секреты. Если результат хуже текущего героя,
  проект просто оставляет прежнюю модель.

- **Распространять стиль слоями:** сначала единые рамки, глубина, палитра и кнопки; затем

## Работа с картинками (обязательно)

- **Никогда не коммить большие PNG/JPG в `public/art/`.** Генерация изображений возвращает PNG ~4 МБ — он нужен только как временный исходник для конвертации.
- **Пайплайн для фона мини-игры:**
  1. `generate_image` → `public/art/<scene>.png` (16:9).
  2. Сразу конвертируй и ужми:
     `convert public/art/<scene>.png -resize 1600x900 -quality 82 public/art/<scene>.webp`
     (проверь, что `convert` из ImageMagick доступен; если нет — `cwebp`).
  3. Удали исходный PNG: `rm public/art/<scene>.png`.
  4. В CSS подключай WebP:
     `background: <fallback> url('./art/<scene>.webp') center/cover no-repeat;`
- **Почему так:** большие бинарники замедляют `git push`, сборку Vite, загрузку артефактов Actions и увеличивают APK на несколько МБ. WebP 1600×900 весит ~100–170 КБ при достаточном для планшета качестве.

- Обрабатывай по одной картинке за раз: генерация и конвертация — самые долгие операции, пакетная обработка увеличивает риск обрыва диалога.
- В headless-скриншотах эмодзи (✕, 💡) могут не отрисовываться из-за отсутствия шрифтов в контейнере — это не баг игры.

Подключение всегда: `background: <fallback> url('./art/<file>.webp') center / cover no-repeat;`, файл 1600×900 WebP q82 ≤ ~170 КБ.

Новые mp3 для существующей главы записываются тем же голосом, что и прежние файлы этой главы. ВАЖНО: при пересоздании песочницы регистрации голосов (voice_id) сбрасываются, и «voice-00» нового диалога может оказаться ДРУГИМ человеком, чем voice-00 прошлых сессий. Поэтому перед записью новой реплики в существующую главу: `add_voice` (женская наррация), владелец сверяет кандидаток НА СЛУХ с эталонным mp3 главы и выбирает совпадающую; при нескольких пробах увеличивай `voice_identity.index`. Если совпадения нет — перезаписать всю главу одним голосом (только по решению владельца). Эталон вступления: `intro.mp3`/`intro_go.mp3` (Рассказчица); `intro_friends.mp3` обязан совпадать с ними.
- **Цепочки голосов `{after:true, then:'file'}` (v0.22.1+).** В `speak()` нельзя ставить два `{after:true}` подряд: оба привяжутся к одному текущему звуку и заговорят одновременно. Для цепочки из трёх реплик используй `speak(b, { after: true, then: c })` — `then` играет после КОНЦА этой реплики. **Ловушка:** в ветке немедленного воспроизведения `speak()` сначала вызывает `stopVoice()` (увеличивает `voiceGen`), а `gen` захватывается раньше — перезахватывай `gen = voiceGen` ПОСЛЕ `stopVoice()`, иначе `then`-цепочка молча гаснет. Вступление использует именно это: `intro.mp3 → intro_friends.mp3 → intro_go.mp3` (при пропуске — `intro_friends → intro_go`). `intro_friends.mp3` — голос voice-00 (Рассказчица): камера интро не показывает Крота/Белку/Светлячка, поэтому про них говорят и предлагают отыскать самим.
- **Проверка голосовых цепочек в песочнице:** `speak` не доступен из консоли (модуль), поэтому живой тест — обёртка `HTMLMediaElement.prototype.play` через `page.addInitScript` (считает воспроизведения и длины src-ов), клики по `#startBtn` → `#select .char[data-char]` (с `{ force: true }` — кнопки анимированы и Playwright ждёт «стабильности» вечно). Тур интро в песочнице в 6–15 раз дольше аудио (время по кадрам), поэтому полный тест цепи — по ветке пропуска `#skipIntro`.
